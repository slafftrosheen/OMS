# Telegram questions and live database context

Selecting `/ask` from the Telegram menu prompts for a question. Send the question as the next private message within five minutes. The session is consumed once; another supported command cancels it. `/ask your question` also works, including multiline questions. Ordinary messages outside a question session are ignored. Sessions are tied to the linked identity, connection version, current role and settings revision. The existing one-minute inference rate limit remains.

The assistant can discover 28 business datasets, read paginated rows, count matching records and group counts by a recorded field. It can retrieve full order specifications and production stages, materials and inventory movements, replenishment, loading, calendar, staff, workforce entries/absences/reports, order history and changes, accessible chat records and company knowledge. Files expose metadata, not storage paths or automatic file-content extraction. Historical revisions expose their identifying information and notes, not unbounded snapshots.

Queries execute inside PostgreSQL under `oms_telegram_reader`, a non-login role without superuser or RLS bypass, inheriting the existing `authenticated` grants and policies. The claim-bound entry point derives the linked identity itself and supplies that identity to the RLS helpers. Source names, columns and filter operators are fixed; the model cannot submit SQL, user IDs for impersonation, credentials or writes. Auth schemas, Vault, integration settings, tokens and connection secrets are excluded. Record visibility is rechecked before subsequent inference and before delivery, including prepared-answer retries. Aggregate query fingerprints are also revalidated; changed aggregate results cancel stale answers. Temporary record references and query fingerprints are cleared on completion.

Pagination and field budgets are explicit. Exact counts apply to matching records visible to the linked account. Partial pages never establish database-wide totals. Records are read on demand; OpenRouter does not hold a direct database connection. AI requires both the company-wide sharing policy and the linked user's personal Telegram AI permission.

Run source/unit tests and Svelte checks before the production build. Database verification is available in `tests/db/telegram-live-context.sql` and `tests/db/telegram-ask-sessions.sql`; it rolls back all changes and sends no messages. It requires an existing linked account and enabled company policy.

Manual acceptance: select `/ask`, send a question in a second message, ask for blocked production stages and stock counts, and verify the cited records in OMS. Verify that workers cannot read another worker's attendance or a chat they cannot access. A real provider response and delivery must be distinguished from mocked regression checks.
