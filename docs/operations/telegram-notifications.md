# Telegram phone notifications

## Delivery status and scope

The repository contains the account-linking UI, authenticated APIs, database migration, trusted notification outbox, and delivery worker. **Live enablement has not been performed as part of this implementation:** no production migration, bot registration, scheduler installation, or real Telegram delivery has been run.

Telegram is disabled by default. Activation requires a deployment operator to complete the steps below. Each user must then opt in from **Settings → Integrations → Telegram**.

The integration forwards notifications generated by these existing server actions:

| Notification type | Existing event | Existing recipients |
| --- | --- | --- |
| `order_pending_review` | A draft enters the review queue | Active Head of Production, Boss, and RD users, excluding the creator |
| `order_confirmed` | An order is confirmed | Creator and assignees, excluding the confirming user |
| `order_cancelled` | A draft or pending-review order is rejected | Creator and privileged reviewers, excluding the actor |
| `consumption_skipped` | A stage is completed without declared material consumption | Active Head of Production, Boss, and RD users, excluding the actor |
| `low_stock` | Recorded consumption leaves stock below its threshold | Active Head of Production, Boss, and RD users, excluding the actor |
| `chat_message` | The order chat service creates a message notification | Order creator and assignees, excluding the sender |
| `rework` | The existing rework service emits a rework notification | Recipients selected by that service, excluding the initiator |

These are event notifications. **No daily calendar digest, scheduled due-date reminder, or automatic loading-day reminder is implemented.** Calendar badges do not themselves create Telegram messages. Room-chat activity outside the order chat notification path is not automatically forwarded.

The recipient must have an active OMS account and an enabled Telegram connection. The existing global `user_preferences.notifications_enabled` flag and per-type `notification_preferences.enabled` opt-outs are respected. In-app notifications remain the primary record; reading or dismissing one before dispatch suppresses its phone delivery.

## 1. Apply the database migration

Apply `supabase/migrations/20261022000001_telegram_notifications.sql` after the existing OMS migrations through the deployment's migration process. Review the pending migration list before running a migration push, since the repository's push script applies all pending migrations in order.

The repository's existing self-hosted workflow is:

```bash
npm run supabase:migrate:list
npm run supabase:migrate:push
```

Run it only in the intended deployment environment, with the established database credentials already supplied securely. Keep `TELEGRAM_ENABLED=false` during migration preparation. Do not paste connection strings containing credentials into shell commands or publish migration logs containing environment values.

The migration creates:

| Table | Purpose |
| --- | --- |
| `telegram_connections` | One private chat per OMS user, with opt-in state and a connection version |
| `telegram_link_tokens` | SHA-256 digests of expiring, single-use connection tokens |
| `telegram_deliveries` | Persistent notification queue, attempts, leases, acknowledgement, and cancellation state |
| `telegram_webhook_state` | Per-chat command ordering metadata that survives disconnect |

These tables have RLS enabled and no direct anonymous or authenticated-client grants. Their RPCs require the service role. Account endpoints validate the active signed-in user before using the server client. There is no automatic Telegram trigger on arbitrary inserts into `notifications`.

## 2. Configure the bot and server environment

Create or select a bot through [BotFather](https://core.telegram.org/bots/features#botfather). Store its token in the deployment's secret manager. Ensure the username belongs to the same bot as the token.

| Variable | Required value |
| --- | --- |
| `TELEGRAM_ENABLED` | `true` only when preparing to activate the complete integration; defaults to `false` |
| `TELEGRAM_BOT_TOKEN` | BotFather token; server secret |
| `TELEGRAM_BOT_USERNAME` | Bot username, ending in `bot`; an initial `@` is accepted |
| `TELEGRAM_WEBHOOK_SECRET` | Random secret of 32–256 characters using letters, digits, `_`, or `-` |
| `TELEGRAM_DELIVERY_SECRET` | A different random secret with the same format; authenticates the scheduler |
| `PUBLIC_SUPABASE_URL` | Existing OMS Supabase URL |
| `SUPABASE_SERVICE_ROLE_KEY` | Existing server-only Supabase service key |
| `PUBLIC_APP_URL` | Optional OMS address reachable from the user's phone; `PUBLIC_BASE_URL` is a fallback |

The two Telegram secrets must differ. A missing or invalid required setting keeps the integration unavailable. All `TELEGRAM_*` settings stay on the server. Never introduce a `PUBLIC_TELEGRAM_BOT_TOKEN` or a browser-facing service key.

Provide these variables to the actual running OMS process. The repository's Compose service forwards the five `TELEGRAM_*` values from its environment or `.env`, with Telegram disabled and credentials empty by default. Recreate the OMS container after changing them. Other deployment methods must supply the same runtime environment and restart the process. Do not run commands that print the resolved environment or secret-bearing Compose configuration into shared logs.

Generate the two secrets locally without printing them. This example creates a new owner-readable file and refuses to overwrite an existing one:

```bash
node --input-type=module <<'NODE'
import { randomBytes } from 'node:crypto';
import { writeFileSync } from 'node:fs';

const output = '/tmp/oms-telegram-secrets.env';
const lines = [
  `TELEGRAM_WEBHOOK_SECRET=${randomBytes(32).toString('base64url')}`,
  `TELEGRAM_DELIVERY_SECRET=${randomBytes(32).toString('base64url')}`,
  ''
];
writeFileSync(output, lines.join('\n'), { mode: 0o600, flag: 'wx' });
console.log('Generated the two secrets in a private local file.');
NODE
```

Import that file into the deployment's secret manager using its secure workflow, then remove the temporary file. Do not commit it. Supply the bot token through the same secret-management workflow, without putting its value in shell history.

`PUBLIC_APP_URL` only controls the optional **Open OMS** button. It may point to an installation reached over the user's VPN. Telegram's inbound webhook requires its own publicly reachable HTTPS address; the entire OMS UI does not need to become public.

## 3. Register the HTTPS webhook

Expose `POST /api/telegram/webhook` through an HTTPS reverse proxy that Telegram can reach. Preserve the `X-Telegram-Bot-Api-Secret-Token` header and the JSON body. Use a valid TLS configuration. The endpoint verifies this secret independently of browser authentication.

After migration and runtime configuration, enable the integration and restart OMS. Set the operator-only environment variable `OMS_TELEGRAM_WEBHOOK_URL` to the complete HTTPS endpoint, including any deployment path prefix. This variable is used by the setup example; it is not a new application setting.

With the bot credentials already loaded into the operator process environment, run the following registration script. It verifies bot identity first, registers only `message` updates, and prints no tokens or raw provider responses:

```bash
node --input-type=module <<'NODE'
try {
  const token = process.env.TELEGRAM_BOT_TOKEN;
  const secret = process.env.TELEGRAM_WEBHOOK_SECRET;
  const username = (process.env.TELEGRAM_BOT_USERNAME || '').replace(/^@/, '');
  const webhook = new URL(process.env.OMS_TELEGRAM_WEBHOOK_URL || '');
  if (!token || !secret || !username || webhook.protocol !== 'https:'
      || webhook.username || webhook.password || webhook.search || webhook.hash) {
    throw new Error('Invalid configuration');
  }
  async function api(method, body = {}) {
    const response = await fetch(`https://api.telegram.org/bot${token}/${method}`, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(body),
      signal: AbortSignal.timeout(15000)
    });
    const result = await response.json().catch(() => null);
    if (!response.ok || result?.ok !== true) throw new Error('Provider rejected setup');
    return result.result;
  }
  const bot = await api('getMe');
  if (bot.username?.toLowerCase() !== username.toLowerCase()) {
    throw new Error('Bot identity mismatch');
  }
  await api('setWebhook', {
    url: webhook.href,
    secret_token: secret,
    allowed_updates: ['message'],
    max_connections: 2,
    drop_pending_updates: false
  });
  const info = await api('getWebhookInfo');
  console.log(JSON.stringify({
    registered: info.url === webhook.href,
    pendingUpdates: info.pending_update_count,
    hasDeliveryError: Boolean(info.last_error_date)
  }));
} catch {
  console.error('Telegram registration failed. Check private configuration and connectivity.');
  process.exitCode = 1;
}
NODE
```

Telegram documents the HTTPS callback, `secret_token` header, update filtering, and retry behavior in [setWebhook](https://core.telegram.org/bots/api#setwebhook). A successful registration is not proof that a user has connected or that outbound delivery works. Inspect [getWebhookInfo](https://core.telegram.org/bots/api#getwebhookinfo) when callbacks do not arrive. This integration uses webhooks; do not run a competing long-polling consumer for the same bot.

## 4. Schedule delivery every minute

Configure a non-overlapping scheduler job to make:

```text
POST /api/telegram/dispatch
Authorization: Bearer <value supplied from TELEGRAM_DELIVERY_SECRET>
```

The secret belongs in the header, never in the URL. The job needs no user session and no bot token. Use HTTPS for a remote scheduler, or a loopback address on the OMS host.

Each invocation examines at most ten eligible-for-processing queue candidates and runs at most two delivery workers. An individual Telegram request times out after eight seconds. Supabase requests have a ten-second timeout. The eight-second bound applies to each provider request, not the entire batch; allow for database latency when configuring the proxy and scheduler timeout.

For example, save this script to the scheduler's managed operations directory, outside secret files:

```js
// dispatch-telegram.mjs
try {
  const target = new URL(process.env.OMS_TELEGRAM_DISPATCH_URL || '');
  const secret = process.env.TELEGRAM_DELIVERY_SECRET;
  const local = ['localhost', '127.0.0.1', '[::1]'].includes(target.hostname);
  if (!secret || target.username || target.password || target.search || target.hash
      || (target.protocol !== 'https:' && !(target.protocol === 'http:' && local))) {
    throw new Error('Invalid scheduler configuration');
  }
  const response = await fetch(target, {
    method: 'POST',
    headers: { Authorization: `Bearer ${secret}` },
    signal: AbortSignal.timeout(180000)
  });
  const result = await response.json().catch(() => null);
  if (!response.ok || !result) throw new Error('Dispatch failed');
  const summary = {};
  for (const key of ['claimed', 'sent', 'retried', 'failed', 'cancelled', 'errors']) {
    summary[key] = Number.isFinite(result[key]) ? result[key] : 0;
  }
  console.log(JSON.stringify(summary));
} catch {
  console.error('Telegram dispatch failed. Inspect scheduler status and private server configuration.');
  process.exitCode = 1;
}
```

Supply `OMS_TELEGRAM_DISPATCH_URL` and `TELEGRAM_DELIVERY_SECRET` through the scheduler's secret environment. An example Linux cron entry uses a private, operator-owned environment file and `flock` to prevent overlap:

```cron
* * * * * flock -n /run/lock/oms-telegram-dispatch.lock node --env-file=/run/secrets/oms-telegram-dispatch.env /opt/oms/ops/dispatch-telegram.mjs
```

Create those paths with permissions appropriate to the scheduler account. Keep the environment file readable only by that account. The example prints aggregate delivery counts only. Do not enable HTTP tracing that records authorization headers, bot URLs, link tokens, or message bodies.

## 5. Connect a user's phone

1. Sign in with an active OMS account and open **Settings → Integrations → Telegram**.
2. Select **Connect Telegram**. OMS creates a ten-minute, single-use connection link.
3. Open the link on the phone, or scan the QR code displayed in OMS. QR generation occurs locally in the browser.
4. In the bot's private chat, press **Start** to submit the connection token. Merely opening the chat does not complete linking. This follows Telegram's [deep-linking flow](https://core.telegram.org/bots/features#deep-linking).
5. Return to OMS. While a link is pending, the settings panel refreshes when visible and on focus; **Check connection** is also available. Confirm that the state is **Connected** before relying on alerts. The bot does not send a separate setup-confirmation message.

One private Telegram chat can belong to one OMS account. Group chats, mismatched sender/chat identities, forwarded commands, and expired or already-consumed links are rejected. A new link replaces the previous pending link; regeneration has a 30-second cooldown. Treat the link and QR as temporary credentials and do not share them.

**Pause** retains the account association, stops new queue entries, and cancels pending or claimed deliveries. **Resume** applies to subsequent eligible notifications; it does not replay cancelled alerts. **Disconnect**, cancelling a pending link, or sending `/stop` in the bot's private chat revokes pending connection links and removes the association. A request already accepted by Telegram cannot be recalled by pausing or disconnecting.

After activation, validate delivery using an ordinary authorized workflow that produces one of the supported events for an opted-in recipient. Also check the phone's Telegram notification permissions and that the bot chat is not muted. OMS does not expose a public arbitrary-recipient test-send endpoint.

## Queue behavior and troubleshooting

| State or symptom | Meaning and next check |
| --- | --- |
| Settings says not configured | Check the actual server environment, enable flag, matching bot identity, required values, and distinct secrets. Refresh after restarting the app. |
| Settings says unavailable | Configuration exists, but the integration tables or database calls are unavailable. Check migration application, database connectivity, and the service key. |
| Connection remains pending | Confirm **Start** was pressed in the correct private bot chat before expiry. Check HTTPS webhook reachability and the configured secret header. Generate a fresh link after the cooldown if needed. |
| Link expires | The QR and open-link controls disappear. Create a fresh link; the expired token cannot be revived. |
| `pending` delivery | Waiting for the scheduler or `next_attempt_at`. Check the dispatch job and queue age. |
| `processing` delivery | A worker holds a lease. A lease older than five minutes can be recovered by a later invocation. |
| Retried delivery | `status` returns to `pending` with a future attempt time. Rate limits honor Telegram's `retry_after`; transport and server failures use bounded exponential backoff. |
| `sent` delivery | Telegram accepted the message and its message ID was persisted. This does not assert that the person read it or that the phone displayed a push banner. |
| `cancelled` delivery | The user paused/disconnected/relinked, became inactive, changed preferences, or read/dismissed the notification before delivery. Cancelled alerts are not replayed. |
| `failed` delivery | The request was permanently rejected, exhausted five attempts, or aged beyond 24 hours. Inspect the sanitized `last_error` code. |
| Connection unexpectedly paused | Telegram returned a blocked-chat response. Unblock the bot in Telegram, then resume or reconnect in OMS. |
| In-app notice exists but no phone queue row | Check opt-in, active user, preferences, and whether the event used a trusted emitter. Arbitrary notification inserts do not trigger phone delivery. |
| Server logs queue unavailable | The trusted publisher falls back to the ordinary in-app insert. This fallback is best effort and does not promise later phone backfill for that event. |

Administrators can inspect aggregate state without exposing notification bodies or chat identifiers:

```sql
SELECT status, count(*) AS deliveries, min(created_at) AS oldest_created_at
FROM public.telegram_deliveries
GROUP BY status
ORDER BY status;

SELECT last_error, count(*) AS deliveries
FROM public.telegram_deliveries
WHERE last_error IS NOT NULL
GROUP BY last_error
ORDER BY deliveries DESC;
```

Run these queries through the normal protected database administration interface. Do not grant browser clients access to the integration tables or RPCs. Fix configuration or workflow problems before considering manual retries; this release provides no automatic replay of terminal deliveries.

The queue provides **at-least-once delivery**. If Telegram accepts a message and the worker crashes before saving the acknowledgement, lease recovery may send it again. The notification UUID prevents duplicate queue entries, but it cannot close that external acceptance/acknowledgement window. The provider's [sendMessage](https://core.telegram.org/bots/api#sendmessage) endpoint has no OMS idempotency parameter. Transient retry timing uses Telegram's [response parameters](https://core.telegram.org/bots/api#responseparameters).

Messages use plain text and are conservatively bounded to 4,000 UTF-16 code units without splitting surrogate pairs. A safe application link appears as a separate button; notification content cannot inject Telegram HTML or Markdown.

## Privacy, ordering, and shutdown

Bot credentials live in server configuration, not database rows or the browser. Connection state contains the private chat/user IDs, optional Telegram username, timestamps, opt-in state, and a version used to invalidate older work. The settings API returns only safe connection status, username, and dates; it never returns chat IDs or token digests. Its responses are private and non-cacheable.

`telegram_webhook_state` retains only chat ID, the latest processed update ID, and message timestamp after disconnect. This ordering fence prevents a retried older `/stop` from removing a newer connection. It also handles Telegram's documented update-ID reset after an idle week. Raw webhook bodies and connection tokens are not stored in this ledger. Do not delete it during ordinary unlinking or queue maintenance.

To stop the integration globally, set `TELEGRAM_ENABLED=false`, restart OMS, and stop the scheduler. Existing account associations and queue rows are retained. If the integration is later re-enabled, still-eligible queued work may resume within its 24-hour lifetime; use individual pause/disconnect controls when opt-ins and queued work must be revoked. Registering or removing the bot webhook is a separate operator action.

## Reproducible verification without live credentials

The focused unit tests use injected fetch/database fixtures and do not contact Telegram:

```bash
node packages/vitest/bin.js \
  tests/unit/telegram-provider.test.ts \
  tests/unit/telegram-service.test.ts \
  tests/unit/telegram-publish.test.ts \
  tests/unit/telegram-api.test.ts
```

The executable migration test loads the actual SQL into an isolated PGlite PostgreSQL database. It checks role grants, token expiry and reuse, chat ownership, trusted publication, opt-outs, queue leases, retries, cancellation, and webhook replay ordering. It uses no production connection or application credentials:

```bash
# Install the verification runtime outside the repository if it is not present.
npm install --prefix /tmp/oms-sql --no-save --ignore-scripts @electric-sql/pglite@0.5.11

OMS_PGLITE_MODULE=/tmp/oms-sql/node_modules/@electric-sql/pglite/dist/index.js \
  node tests/integration/telegram-migration.mjs
```

PGlite is not an application dependency. `OMS_PGLITE_MODULE` accepts another installed module entry when `/tmp/oms-sql` is unavailable. The isolated database exercises PostgreSQL function behavior and permissions; it does not replace a deployment smoke check or simulate concurrent production processes.

The settings and calendar browser fixtures are in `tests/e2e/calendar-telegram.spec.ts`, served by `tests/ui/playwright.config.ts`. With Playwright's browser installed, run:

```bash
npx playwright test --config tests/ui/playwright.config.ts tests/e2e/calendar-telegram.spec.ts
```

Run the normal source/unit suites, type check, and production build as part of release verification. Live account linking, phone delivery, and deployment-specific networking remain activation checks for the operator; they are not implied by the isolated tests.
